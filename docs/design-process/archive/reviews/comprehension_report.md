**What this proposes**

p2prdf lets World of Warcraft Forever players find a five-player dungeon party (1 tank, 1 healer, 3 damage dealers) with no hosted matchmaking service. A WoW addon (`P2PRDF`) turns the live character into a copyable text code and a QR code. A Tauri desktop app takes the pasted code and joins a peer-to-peer network. In that network, peers on the same `region + realm + faction + dungeon` topic gossip search ads and run the same deterministic function each epoch to propose parties. Players then press Confirm, and the app shows each member's claimed character name so they can invite each other in game. A phone can use the same web app, served by the desktop app over the LAN and approved by a per-install token from a pairing QR. Peers find each other first through remembered peers, then peer exchange, and last through a few trusted peers whose keys are built in. The detailed plan is one new repository, `forever-together`, with the addon, a one-crate Rust app, a React web app, a shared code spec with test vectors, and a test VM pulled in as a git submodule.

**How the existing system works, per this document**

The only existing system described is `wow-forever-addons`. It holds Social Hub and other addons, and it also holds a headless Lua test VM (`wowluavm`). That VM has a `prelude.lua` and a `main.rs`, and its `./run-tests.sh` must keep passing. The VM can read `wow-forever-api.json`, an export of the client API. The WoW client lets an addon read character data but not use the network or write files while the game runs. `SavedVariables` is written only on `/reload` or logout. The document says it cannot confirm what the real client returns for names, realm and region, item level, or faction. Finding a group today is assumed to be shouting in chat, and the document flags that this is unchecked (line 23). The document uses a template repository at `git.lloopback.com`, with Tauri 2, React, Storybook and mise.

**Findings**

1. **Blocker.** Lines 193, 199-205, 213 and 441 (the ad and widening mechanism). The epoch is described inconsistently. Line 199 says "a few seconds". Line 441 sets it at 10 s. The ad keep-alive is 30 to 60 s at line 193 and 45 s at line 441. More seriously, the party-building rule in step 3 says compatibility is judged under "their ad's own constraints". Line 195 says the schedule is shared and the stage is in each ad. The document never says whose stage applies when two peers are at different stages. It also does not say how a party is "relaxed after a wait" (line 203) relative to the stage table. A reader cannot say whether two peers compute the same party, which is the whole agreement claim.

2. **Blocker.** Lines 205 and 209 (commit and Confirm). Step 5 says a party is committed when announcements from all five members have been seen, and the peer then "stops searching and ignores other parties' invitations". Line 209 then says the party is final only after all five confirm, and a peer may already have announced a different party in a later epoch. This can leave a peer in two commits, which the Goals (line 37) rule out. Line 209 resolves it as "the one-party guarantee holds at the confirmation step". The goal wording ("never in two committed parties") and the behaviour conflict. It is also unclear whether a committed peer keeps announcing, and whether the Decline message (line 426) is sent on timeout or only by the user.

3. **Major.** Lines 13 and 148-157 (the code format). Lines 14-15 and 29 call the code something the player "scans as a QR". The phone scan only yields text, which the user must paste. That is clear later but the overview reads as if the QR is scanned straight into the app. The Goals list at line 31 also names the contents differently from the field list at lines 148-157 and the table at lines 395-411. The two lists disagree on whether realm and region are separate "opaque" values, and the table has no "dungeon" field. The window description at line 496 says it shows "dungeon", but the code has none (line 155).

4. **Major.** Lines 17 and 64-66 (realm and region). "Realm" is defined as a ruleset (PvP, PvE, and so on), and "region" is never defined beyond a client call. The counts at line 169 ("5 realms, 2 regions") are not tied to a list of regions. Realm in the code is an opaque string compared as given (line 152). The topic needs exact equality, yet the value set is unknown (line 66). The reader cannot tell how two peers are sure to produce the same topic string.

5. **Major.** Lines 169 and 419 (shards). Line 169 says a peer's shard comes from its peer ID, so a peer sits in exactly one shard. Line 195 and the stage table (line 441) say widening joins "other shards of the topic". The document does not say which shards a peer joins at stage 4, or how ads from other shards reach its sample. The shard table is also never specified. Line 71 treats the shard counts as unknown, yet they are part of the protocol version.

6. **Major.** Lines 17, 34 and 165 (the dungeon table). The "faction hint" is defined at line 17, but its effect varies. Line 165 says it only orders dungeons. Line 417 gives a different ordering from line 165: zone first, then the distance of level from the range middle, then the faction hint. Line 165 says zone first, "followed by the rest", with no mention of the middle-distance ordering. Line 34 says "proximity to each dungeon's zone", but line 165 says there is no distance calculation, only a name match. The "slack" at the edges (line 165) is given as 3 only at line 417.

7. **Major.** Lines 178 and 179 (bootstrap). The ordering "remembered, then peer exchange, then trusted" is clear. Peer exchange asks "peers it is already connected to", but a cold-start peer with no remembered peers has none. Step 2 therefore depends on step 1 succeeding. The text of step 3 says a trusted peer is used "only when every remembered peer is unreachable and no neighbour could help", and CUJ 4 shows first start going straight to trusted. The "stop at the first that works" rule is never defined (what counts as "works": a dial, or a peer in the topic?). Line 178 says an entry counts as live only after the other side says it is in the topic.

8. **Major.** Lines 187 and 189 (iroh address lookup). "iroh's address lookup" and the "public DHT" are used at lines 19, 134 and 179 without a definition. The reader is told the DHT gives no topic-keyed lookup (line 187), but is not told what iroh's address lookup does beyond resolving a key to addresses. iroh, iroh-gossip, `varaq` and "relays and hole punching" appear with links or one-line glosses only in Additional Resources (line 357). `varaq` is defined there at line 357 but used from line 44.

9. **Major.** Lines 421 and 183. Gossip authentication: the document says every message carries a signature, "to be confirmed in the spike". The design depends on it, and line 183 says peers cannot prove topics. It is not said what happens if the spike fails.

10. **Major.** Lines 513-516 (the submodule and `wow-forever-addons`). The overview at line 372 says `wow-forever-addons` has its addons "unchanged", but item 11 modifies `prelude.lua` and `main.rs` there, and line 240 says the design "does not touch" that repository. This contradicts itself. The reference to that repository's `CLAUDE.md` is not followed by what the "C_ wrapping block" rule says.

11. **Major.** Line 372 and lines 513 and 523. The ADR numbers (`adr/0001` to `adr/0022`) and the files `concepts_brief.md`, `design_draft.md` and `wow-forever-api.json` are referenced as if the reader holds them. `adr/0022` is cited for name calls at line 65, and its content is not summarized. It is unclear whether the ADRs are required reading.

12. **Major.** Lines 23 and 413 are authorial hedges inside the proposal ("I have not checked", "from my memory of the QR tables"). First-person "I" is not defined as the author, and an unverified claim sits inside normative text. The QR capacity claim (about 70 characters in version 4 or 5) is unchecked, and the `Interface: 16001` value at line 476 is given with no explanation.

13. **Major.** Lines 331 and 346 (token rules). The NFR at line 346 says "a bearer token on every route except the static files" and that trusted-peer changes accept only loopback. Line 220 says the desktop window gets the token from the app, and line 548 shows it in a URL fragment. The phone and the desktop window use the same API, so how a route can be "loopback only" for a desktop window running in a local process is never explained. The LAN mode listens on `0.0.0.0`, which means requests from the LAN can arrive on a non-loopback address. This is clear enough, but not the reason `GET /api/pairing` is safe from the same device's browsers.

14. **Nit.** Line 14, "the author's template", and line 356. The template is linked once, at line 356, so earlier uses (lines 14 and 215) refer to it before it is identified. "Atoms, molecules, organisms" at line 593 is the template's atomic design, which a general reader may know but cannot confirm without the template.

15. **Nit.** Line 64: `forever-together` is called "the repository" before it is introduced at line 372, and the draft describes the addon at line 13 as being "in the same repository as the app" without naming it.

16. **Nit.** Line 441: stage numbering. Line 102 lists stages by name, "secondary roles, item level range, level spread, more shards, more dungeons". The table has item level ±15% at stage 0 and level spread ≤ 3 in stage 0, which is not "starts strict and relaxes" in the order stated at line 35 (item level and role, then level spread). Stage 0 already has a level spread and the ordering in line 35 omits it.

17. **Nit.** Lines 17, 169 and 415. The numbers of dungeons differ in places: "20 dungeons marked available" at line 169 and "29 entries" at lines 415 and 603. The arithmetic "about 400 topics" at line 169 is 5×2×2×20, which is exactly 400. Line 287 says Alternative F has "about ten times more topics", with no basis given.

18. **Nit.** Line 45 and line 621 ("every item in the test lists above exists and passes"). Line 603 ends a sentence with a stray space before the full stop ("the schedule ."), and `test_window` at line 511 says "the number of QR textures equals the number of dark modules", but line 496 says the quiet zone and pooled textures are used. This is fine, but a reader cannot tell whether the quiet zone counts.
