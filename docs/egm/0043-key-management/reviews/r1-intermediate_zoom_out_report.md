## New findings

**N1 (Major), lines 51, 98, 254-259 (build order), 273: the `varaq` check must be a hard gate before any Part 1 code.** It reinforces Z1 and fixes the ownership problem in P8. The check is assigned to ticket 0003, a "new small ticket" (line 127), a `spike-s0.md` row (line 210) and line 98's interim notice, while line 119 says 0003 only records file modes. Name one owner and make it step 0 of the build order. Keep the interim notice: Decision 6 plus a notice printed forever is a patch over an unknown. If the check cannot be done first, say Decision 6 is not yet decided. `VaraqStore` (`app/src/store/varaq_store.rs:17`) holds an in-process `Mutex<Db>` and nothing else the reviewer could see; treat "no cross-process lock" as the likely case. Then the fallback "reopen the decision" is the probable path, and the draft should say which fallback it prefers.

**N2 (Major), lines 94, 219, 226; `runtime.rs:127-130`, `identity.rs:85`: raises C5 from Nit to Major and merges it with Z2.** The deploy story (line 172) is `key import` before first start on a cloud volume. Any prior `key show`, `--print-public-key` or `key export` on that volume creates a random key (`load_or_create`), and import then fails without `--force`: the primary path has a footgun that only a README line can prevent. Fix: read paths (`show`, `export`) return a "no key yet" error and do not create a key; a normal start creates it. This removes the "read-only but writes" contradiction in Z2. C5's liability (`--print-public-key` loses create-on-first-use) touches `README.md:58,69`, `CLAUDE.md:89`, `tickets/0008` and `runtime.rs:126`, all of which already change (lines 206-208). The cheaper alternative, letting `import` proceed without `--force` on an auto-created, never-used key, cannot be detected, so the read-path split is recommended.

**N3 (Nit), lines 95-96, 227-234: recovery from a corrupt stored key.** `Identity::load_or_create` returns `BadStoredKey` on a wrong-length value (`identity.rs:58,88,148`). `reset` and `import --force` are the natural repair, but both print the "old peer id", which requires decoding the old key. State that a corrupt old key prints "unreadable" and does not block the replace.

**N4 (Nit), line 203: Z6's supporting claim does not hold.** Z6 says `runtime::open_store` "already does `create_dir_all`" as a reason to prefer it; `VaraqStore::open` already calls `create_dir_all` (`varaq_store.rs:46`), so `open_store`'s call is redundant and deploy-before-first-start works either way. The remaining argument against bypassing `open_store` is weak: it is an `Arc::new` wrapper around the same open call.

## Rulings on the Stage 5 mitigations (zoom-out lens)

* **C1 (separate X25519 intake key): net simplifying; keep Major and put it to the author as an explicit decision.** It removes the `age` `ssh` feature, so `rsa` and RUSTSEC-2023-0071 leave the app (Z3, the line 53 question); removes the Ed25519-to-X25519 conversion as a correctness risk (Z4); makes the line 37 goal testable without the app's key; and removes the coupling lines 138 and 115 admit (reset, import and server compromise would no longer touch export readability). Cost: one more compiled-in constant and one more offline secret. The author already rejected "a separate key"; present C1 as the same decision with the dependency cost now priced in. If the author declines again, record the `rsa` / `ssh` feature as an accepted cost in line 138. Either way the ADR text must not claim the conversion "adds no custom cryptography" while leaving the `rsa` pull-in unmentioned.
* **C2 (watchdogs: polling for key changes, `--expect-peer-id`): reject; YAGNI and built on the unverified `varaq` fact.** (a) Polling cannot detect a second process's write if `varaq` allows two openers and the store caches; it cannot be designed before N1's check, and adds restart-loop risk. (b) `--expect-peer-id` adds a start-up input, contradicting Decision 4 and the cost accepted at line 172. The cheap half is free: headless already logs its peer ID at start (`runtime.rs:209`); add a README line telling the deployer to compare it with `BUILTIN`.
* **C3 (`--save-old` / `--discard-old`): reject, conditional on Z5.** It adds flags and a secret copy to guard against a typo; the refusal without `--force` and the confirmation already guard it. If `reset` is cut, only `import --force` remains and the case is thin. A README line "export before you force-import or reset" gives the same benefit. Stays Nit; recommend not adopting.
* **C4 (standby trusted key in `BUILTIN`): reject for this design.** Speculative; Non-Goals line 43 already excludes rotation without a release; it adds a permanent secret trusted by every shipped build. If wanted, it belongs in ticket 0008. Keep one cheap piece: state in line 115 that old builds fall back to remembered peers and peer exchange (ADR 0023).

## Overall

The draft is already over-detailed, and adopting the mitigations would grow it. The recommended triage keeps it the same size or smaller: adopt N1 (as a gate), N2 and N3; decide C1 together with Z5 and Z3; reject C2, C3 and C4. With C1 adopted and `reset` cut, Part 2 shrinks to a one-paragraph interface note (Z3), the line 52-53 questions mostly disappear, and C3 vanishes. Before the next stage, `--stdout` (P4) and the dispatch owner (P5) must be fixed in the text, or the findings will be applied to an ambiguous baseline.
