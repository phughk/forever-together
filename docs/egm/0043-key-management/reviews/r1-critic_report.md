## Design critic (`egm-design`)

Not read by the reviewer: `app/src/net/iroh_net.rs`, ticket 0009, `varaq_store.rs`; claims about them are unchecked. No Blockers.

- **D1 (Major), lines 29-189: no Risks & Mitigations section.** The standard requires failure modes, security implications and mitigations. Risks sit as "Cost accepted" bullets (138, 158, 172, 179) with no mitigation. Gather them; entries needed for D3-D8.
- **D2 (Major), lines 137, 144, 151, 157, 164, 171, 178: "Rejected by author" rationales cite no link and are partly circular.** Line 137 says a second key "adds nothing they need" while line 138 lists what it would add (a server compromise would not expose every export; old exports would survive a reset). Line 144 ("not needed once the first alternative was declined") is circular. Link ADR 0038's amendment and ADR 0039 as the record and state the technical trade-off as the reason.
- **D3 (Major), lines 37, 106-108, 138: no forward secrecy and no mitigation for a later key leak.** Exports are public and permanent on GitHub, encrypted to the key of an internet-facing trusted node whose secret is also in backups and on a decrypting workstation. If that key leaks, every past export is readable retroactively; `key reset` does not help. Cheap mitigation: decrypt only on an offline machine; add to the README process (line 114) and state the residual risk.
- **D4 (Major), lines 106-108, 113: `BUILTIN[0]` is never checked to be a key the author holds.** Files are posted publicly before anyone tries to decrypt; a mistyped `BUILTIN[0]` that is still a valid point makes every export silently undecryptable. Add a release gate: a test that `BUILTIN[0]` is a valid ed25519 point, and a documented encrypt-and-decrypt with the real backed-up key before shipping ticket 0044. Line 109 proves the path only with a throwaway key.
- **D5 (Major), lines 98, 113-114, 51: the backup flow contradicts the running-app guard.** Line 98 says `key show` and `key export` "only read, and are not guarded", but both open the store through `open_store` (`runtime.rs:121`). If `varaq` refuses a second opener (decision 6's assumption), read commands fail while the node runs, and the documented backup ("on the always-on node ... `key export`") needs the node stopped; the design does not say so. If `varaq` does not refuse, import and reset can run against a live node that holds the old key in memory (`build_network` loads the identity once). State both cases. Verify the `varaq` behaviour before the design leaves "Proposed", not as a deferred ticket.
- **D6 (Major), lines 95-96, 115: destructive commands have no safety net for the key that matters.** `key reset --yes` and `key import --force` replace the secret with nothing saved; only peer IDs are printed. The app can compare the current peer ID with `trusted::BUILTIN` and warn loudly (or require an export) when replacing a built-in key, or write the old key to a timestamped file first. Specify that reset is one `put`, not delete then put (line 95 says it for import only).
- **D7 (Major), lines 63, 171-172: a headless node with no import silently generates a new identity.** For the trusted node this silently breaks the bootstrap fallback. Mitigate with a start-up log of the peer ID, or an opt-in flag or setting that refuses to auto-generate. Today's headless path (`runtime.rs:192-193`) always calls `load_or_create`.
- **D8 (Major), lines 15, 107: two external capability claims are unverified.** The `.age` armor "pasted into an issue as text or attached as a file `scans-<date>.wowft-scans.age`": GitHub limits issue and comment bodies to 65,536 characters (ADR 0038 leaves the size cap undecided; armor adds about 33%), and accepts only an allowlist of attachment extensions (reviewer believes `.age` is not on it; verify). Settle with a size cap, a `.txt` suffix and a documented fallback.
- **D9 (Major), lines 52-53, 106: Cargo dependency risk for `age` and its `ssh` feature.** `age` is beta; its `ssh` feature pulls in `rsa`, which to the reviewer's knowledge has an open advisory (RUSTSEC-2023-0071, Marvin timing attack) with no fixed release. Check `cargo audit` or `cargo deny`. Without the `ssh` feature the design would need the custom Ed25519-to-X25519 conversion that line 185 says it avoids; record that trade-off in Alternatives. The open choice between `ssh-key` and the `age` parser risks two OpenSSH parsers in one binary.
- **D10 (Nit), line 109: the round-trip test proves less than claimed.** It uses the Rust `age` library, not the `age` or `rage` binary the author will run. Add a one-time manual check with the real `age -d -i`, or a fixed vector from the Go tool.
- **D11 (Nit), lines 107, 115: rotation of `BUILTIN` has no key-retention rule.** The header key tag helps only if old private keys are kept; installs on older releases keep encrypting to their compiled-in `BUILTIN[0]`. The README process should say to keep every historical `BUILTIN[0]` secret.
- **D12 (Nit), lines 35, 94: owner-only creation is not specified as atomic.** Create with mode 0600 at open time (`create_new`); setting permissions after writing leaves a readable window.
- **D13 (Nit), lines 34, 63, 94: `--stdout` can leak the secret into logs** (CI, terminal scrollback), against the goal at line 34. Consider refusing `--stdout` on a TTY without `--yes`.
- **D14 (Nit), lines 61, 94, 97: command-line grammar is under-specified.** `key export <file>` and `--stdout` appear as alternatives without saying whether the file argument is optional; `--data-dir` must be `global` for `key import --data-dir ...`; precedence among `--print-public-key`, `--headless` and the subcommand is unstated (the test `print_public_key_wins` implies a rule); ticket 0043 lists `--public` as settled while line 54 keeps it open.
- **D15 (Nit), line 93: `key show` and `key export` on an empty store generate a key** (today's `public_key()` goes through `load_or_create`). State whether `export` does the same; note that `import` after any earlier `key show` needs `--force`, which surprises the "before its first start" deploy path (line 63).
- **D16 (Nit), lines 55, 94: Windows exports are unprotected.** Line 94 promises owner-only only on Unix; on Windows an exported plain key relies on the parent directory's ACL, and Windows OpenSSH may refuse a loosely protected key.
- **D17 (Nit), lines 35, 119: permissions are inconsistent.** The export is made owner-only but the store's own copy of the secret is unchecked (ticket 0003). The export's mode protects nothing if the store file is world-readable; say so.
- **D18 (Nit), line 187: alternatives missing for key format and backup method.** The only format alternative is raw hex; PKCS#8 PEM is a realistic competitor (reject for `age` and ssh interoperability). The simplest backup alternative is absent: copy `identity/secret` or the data directory with no export code.
- **D19 (Nit): stale and inconsistent metadata and wording.** Line 4 ("not yet reviewed with `egm-review`"); line 38 ("collapse into one") against lines 121-127; line 119 (0003 shrinks) against ticket 0003's current text; line 7 omits ADR 0016 and line 47 cites ADR 0034 unlisted; line 131 mixes "I" and "the author"; line 144 never says which two keys the sealing scheme would use.

## Structural (`egm-structural`)

Heading hierarchy is sound; no skipped levels; the mermaid fence is closed. It read only the draft and the standard.

- **S1 (Blocker), expected between lines 128 and 129: missing required section, Risks & Mitigations.** The standard's "Risks & Limits" requirement has no heading in lines 1-190. Risk material is scattered across "Cost accepted" bullets (138, 158, 172, 179), Goal 35, Non-Goals 42 and Open Questions (51, 55), never as failure mode plus mitigation. Failure modes implied but never stated: key loss or leak; a partial write during export or import; a second process opening the store (unverified, line 51); a compromised trusted node exposing identity and exports (138); a beta `age` or `ssh-key` crate pulling `rsa` (52-53).
- **S2 (Major), lines 131, 137, 144, 151, 157, 164, 171, 178: rejections attributed to the author with no linked issue, discussion or PR.** Seven of nine entries; lines 35 and 42 ("decided by the author") likewise. Link the record (ADR 0039, ticket 0043, only if they record the decision) or restate each as a technical or scope trade-off; several entries already do (165, 185).
- **S3 (Major), line 66: no section named "Proposed Architecture".** Content exists (diagram, Commands, Key file format) under "Technical Plan", which also holds process and ticket planning ("Tickets after this design", lines 121-127; "Permissions", 117-119). Rename or split, and move the ticket content out.
- **S4 (Major), lines 49-64, 51: Decisions follow Open Questions and are referenced before they are defined.** The first open question cites "decision 6" before the Decisions list; decisions 5 and 6 are marked "(Resolved from ADR 0039)", so they are not open items. Put Decisions before Open Questions and Open Questions last, before Alternatives.
- **S5 (Major), lines 129-189: the Alternatives section is mixed and lacks a uniform shape.** The intro is first person ("I considered", "I put to them"). Entries vary (Rejected / Cost accepted / Why weaker; only Rejected at 151; only Left out at 185, 189; the 189 entry has no description and no cost). "Left out" is used as a rejection verdict. Use one template (Description, Verdict, Reason, Cost); drop the first person.
- **S6 (Nit), lines 64, 98:** decision 6 says "no warning-only mode"; line 98 says the commands also print a stop-the-app notice until verified, effectively a warning-only mode. State once which applies and when.
- **S7 (Nit), lines 54-55:** line 55 (Windows) is a statement plus a to-do, not a question; line 54 asks about `--public` while line 94 treats it as settled. Rephrase or move to Risks.
- **S8 (Nit), lines 94, 97-98:** one bullet carries `key export <file>`, `--stdout` and `--public` without saying whether the file is required with `--stdout` or whether the two flags combine. Split into sub-bullets or a flags table; "Where they live" and "Running app" are not commands and belong under their own H3.
- **S9 (Nit), lines 6-7, 42, 47, 113, 119, 123-127:** plain-text, unlinked references to tickets 0003, 0008, 0009, 0040, 0044 and ADRs 0008, 0034; ADR 0034 missing from "Related decisions". Use one relative-link style.
- **S10 (Nit), line 125 (and 7, 193):** "0040" and "0039" do not say ADR or ticket; line 127's "New small tickets" has no number or name. Prefix each.
- **S11 (Nit), lines 72-89:** the diagram has no node for the `BUILTIN` flow or the running-app guard; `F --> A` is redundant with `X -->|age -d -i| A`; no caption.
- **S12 (Nit), lines 3-7:** line 4's "not yet reviewed" will go stale; the header has no review-round field.

Required sections against the standard: Problem Statement (line 17, yes); Goals & Non-Goals (29, 40, yes); Proposed Architecture (content yes, heading no, S3); Alternatives Considered (129-189, with attribution gaps, S2, S5); Risks & Mitigations (no, S1).

## Style (`egm-style`)

Read: `runtime.rs`, `cli.rs`, `identity.rs`, `trusted.rs`, ADR 0038, ADR 0039, tickets 0003 and 0043. Not read: ADRs 0008, 0016, 0023, 0036, `lib.rs`, `store/mod.rs`, tickets 0008 and 0044. No Blockers.

- **T1 (Major), lines 54, 93: the claim about `key show` and today's output is false.** Line 93 says `key show` prints hex plus the OpenSSH public line, "Same output as today's `--print-public-key`"; line 54 says it "already prints the public line". `runtime::public_key` (`runtime.rs:127-130`) returns only `peer_id().to_hex()` and `lib.rs:48` prints that one string. The OpenSSH line is new, so the alias changes its output, a compatibility decision the draft does not mention. State that `key show` adds the line and whether the alias prints the old or new output.
- **T2 (Major), line 107: refers to a header that no longer exists.** The draft says `age` "replaces the custom header sketched in the ADR 0038 amendment", but ADR 0038 line 41 now says "There is no custom header." Remove or reword as history.

Name the decision the beta status and `rsa` pull-in feed (accept, pin a version, or choose `rage`), who decides and when; mark dependent plan sections provisional.
- **T4 (Major), lines 109, 179: a planned test is described as existing proof.** "so the workflow is proven" and "is what proves it works", but the test does not exist (dependencies are not in `Cargo.toml`) and uses the `age` library, not `age -d -i`. Say "will test" and that it covers the library path only; narrow the claim at line 102 or list a manual CLI check. Ticket 0043's done-when covers `ssh-keygen -y -f` but not the `age` CLI.
- **T5 (Major), lines 55, 119: ticket 0003 contradicts the design's scope.** Line 119 shrinks 0003 to recording file modes; the ticket still says to check that the store holds the key with restrictive permissions. Line 55 states the Windows default as fact and then says to confirm. Calibrate line 55 to "expected; to be confirmed" and update ticket 0003.

- **T7 (Major), lines 19, 28: the Problem overstates.** "nothing else can be done with it", but `--print-public-key` exists (`cli.rs:13-15`; line 93 acknowledges it). Add "except print its public half".
- **T8 (Nit), line 4:** status text goes stale after this review.
