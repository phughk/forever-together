# Verifying the addon installer on a real install

*   **Author:** Hugh Kaznowski
*   **Status:** Initial draft, unreviewed
*   **Date:** 2026-11-22
*   **Ticket:** [ticket 0006](../../../tickets/0006-verify-addon-installer-real-install.md). Blocks [ticket 0007](../../../tickets/0007-addon-installer-stage-2.md) (native dialog, Linux detection, first-run step).
*   **Related decisions:** [ADR 0028](../../adr/0028-the-desktop-app-installs-the-bundled-addon.md) (its last section lists the unverified assumptions this plan checks), [ADR 0002](../../adr/0002-addon-shows-data-only.md), [ADR 0020](../../adr/0020-one-new-repository-standalone-addon.md). Where this document and an ADR disagree, the ADR wins.

## Overview

The Settings page has an Addon card. It calls three loopback routes (`GET /api/addon`, `PUT /api/addon/folder`, `POST /api/addon/install`, in `app/src/server/addon_routes.rs`) that use the module `app/src/addon_install.rs`: validate an `.../Interface/AddOns` folder, compare the installed `ForeverTogether.toc` version and files with the bundle, and install by staging into `.ForeverTogether.new`, renaming the existing folder to `.ForeverTogether.old`, renaming the stage into place and removing the old one. The bundle is generated by `app/build.rs` from `addon/ForeverTogether/`. The unit tests use temporary directories and injected environments; no real game folder has been used beyond the author's macOS machine, where `/Applications/World of Warcraft/_forever_/Interface/AddOns` was observed (one observation).

This draft is the manual checklist the ticket asks for, with exact steps and pass criteria, and what changes after each answer.

## The Problem

ADR 0028 lists these as unverified, and the code carries each as a guess:

| Unverified fact | Where the code assumes it |
|---|---|
| The Forever folder layout beyond one macOS machine | `MAC_SYSTEM`, `MAC_HOME_REL`, `WINDOWS_REL` and the `Interface/AddOns` shape check in `validate_folder_with_home` |
| Windows default paths | `WINDOWS_ENV_BASES` (`ProgramFiles(x86)`, `ProgramFiles`) joined with `World of Warcraft`, `_forever_`, `Interface`, `AddOns` |
| Linux paths | `Os::Linux` returns no candidates; the paste field is the only route |
| Game behaviour during an in-place swap | `install_bundle` renames while the game may be running |
| Windows file locking and admin rights | the `addon_locked` and `addon_permission_denied` error codes exist but were never triggered by a real lock |
| Dot-prefixed folders ignored by the client | `STAGE_NAME` and `OLD_NAME` are `.ForeverTogether.new` and `.ForeverTogether.old` inside the AddOns folder |

## Goals

*   An answer, with the date and the platform, for each row, recorded in ADR 0028 (the ticket's done-when).
*   Detection fixed where it was wrong, for the platforms tested.
*   A short list of platforms and cases that remain untested, written down rather than implied.

## Non-Goals

*   The native folder dialog, Linux auto-detection and the first-run step (ticket 0007; this ticket's answers feed it).
*   Release tracking, auto-update, uninstall, backups (ADR 0028 out of scope).
*   Changing the addon.

## Technical Plan

### Setup

*   A build of the app from the commit to be tested (record the commit and the bundled version, which the Addon card shows).
*   For each platform: a machine with a Forever client installed in the normal way, and a character that can log in.
*   Start each case from a known state: no `ForeverTogether` folder in the AddOns folder, or a copy of an older version (edit the `## Version:` line of the `.toc` copy to `0.0.9` to get `update_available`).
*   Before every case record the AddOns folder listing (names only) so changes by the installer are visible.

### Checklist

Each case has a pass criterion. A fail is recorded with the exact message and the `detail` field the UI shows under Details.

| # | Case | Steps | Pass |
|---|---|---|---|
| 1 | **macOS layout and detection** | Start the app with a clean data directory; open Settings, Addon card | The card offers exactly the real AddOns folder ("Use this folder?"), the status is `not_installed`, and confirming installs; after `/reload` in the game, `/wowft` opens the window |
| 2 | **Layout on the author's other macOS installs** | If the client exists under `~/Applications/...` (`MAC_HOME_REL`) test it too | Same as 1 |
| 3 | **Windows layout and detection** | On Windows, a client installed under Program Files (x86) or Program Files, and one installed elsewhere (another drive) | The default location is detected, or absent with the paste field working; record the real path, and whether `_forever_` is the real folder name |
| 4 | **Windows admin rights** | Install into `Program Files (x86)` as a standard user and as an administrator | A standard user either succeeds or gets `addon_permission_denied` with a plain message; the old copy is untouched on failure |
| 5 | **Windows file locking** | Install while the game is running, at the login screen, logged in at the character select screen, and in the world | Each result recorded: success, or `addon_locked` / `addon_permission_denied`; on failure the previous `ForeverTogether` folder is intact and the stage is gone |
| 6 | **Swap while the game runs (macOS)** | Install a changed version while the client is logged in and in the world; do not `/reload`; then `/reload` | No crash, no Lua error caused by a half-written folder at the moment of the swap; after `/reload` the new version is loaded (the `/wowft` window text or the version in the AddOns list changes) |
| 7 | **Dot-prefixed folders ignored** | Create `.ForeverTogether.new` and `.ForeverTogether.old` by hand (copies of the addon) in the AddOns folder; start the client; open the AddOns list at character select; log in | The client lists no entry for either folder, loads nothing from them, and the real `ForeverTogether` loads once |
| 8 | **Leftover cleanup** | Leave a hand-made `.ForeverTogether.new` and `.ForeverTogether.old`, then install from the app | Both are removed and the install succeeds |
| 9 | **Linux** | On a Linux machine with the game through Wine or a launcher: find the real AddOns path; paste it into the card | `validate_folder_with_home` accepts it (the path ends in `Interface/AddOns`) and the install works. Record each launcher layout seen |
| 10 | **Symlinked dev copy** | Make `ForeverTogether` a symlink to the repo folder; use the app | The app refuses with the "is a link" message and leaves it alone |
| 11 | **Path forms** | Paste a path with quotes, a `~` prefix, trailing slash, a path with spaces, and on Windows a path with backslashes and a drive letter | Accepted or refused as ADR 0028 states; record any mismatch |

### What to record, where

*   ADR 0028, "Unverified assumptions": replace each line with its answer or a dated amendment saying "verified on <OS version> by <test>". ADRs are immutable except by amendment, so use an amendment block with the date.
*   If a candidate path was wrong: the table of candidates in `app/src/addon_install.rs` (`MAC_SYSTEM`, `MAC_HOME_REL`, `WINDOWS_ENV_BASES`, `WINDOWS_REL`) and its tests.
*   `docs/spike-s0.md` is not the place: the ticket's done-when names ADR 0028.

### What changes on each outcome

*   **Case 7 fails** (the client reads dot-prefixed folders): the stage and old names must change; see open question 2.
*   **Case 5 or 4 fails on Windows:** the error codes and their messages may need rewording, and the product may need a fallback (open question 3).
*   **Case 6 shows a crash or load error:** the swap strategy changes (open question 2 also covers this) and the README step 2 ("type `/reload`") may need a warning to install with the game closed.
*   **Case 1 to 3 detection wrong:** the candidate table changes; tests that pin the candidates change with it.

## Alternatives Considered

*   **Test only with unit tests on temporary directories.** This is the current state and cannot answer the six rows above.
*   **Run on virtual machines.** Not rejected, but a licensed client and account are needed on each, which the author may not have for Windows.
*   **Ask players to test.** Possible after a release; it needs an issue template and a way for players to report the real path (Settings shows the pasted path). Raised in open question 1.

## Detailed Implementation

The run changes nothing before its results. Files touched afterwards, only where a result requires:

*   `docs/adr/0028-the-desktop-app-installs-the-bundled-addon.md`: amendment with the answers and dates.
*   `app/src/addon_install.rs`: candidate constants; `STAGE_NAME` and `OLD_NAME`; the `install_bundle` order of renames; error mapping (`AddonError::from_io`) for Windows lock errors; matching tests in the same file.
*   `app/src/server/addon_routes.rs`: none expected.
*   `webapp/src/components/organisms/AddonSettings.tsx` and its story: messages, only if an error needs new wording.
*   `README.md` ("Getting your character code and QR in game", step 1 and 2): if install while the game runs needs a warning.
*   `tickets/0006-verify-addon-installer-real-install.md`: status; `tickets/0007-addon-installer-stage-2.md`: unblock, with the Linux layouts seen.
*   `scripts/install-addon.sh`: none (developer script, uses `rsync --delete` on a folder the developer names).

## Test and verification plan

*   Before the run: `cargo test --lib addon_install` and `cargo test --lib server::` (the routes tests) pass; `cargo clippy --all-targets -- -D warnings`.
*   Each case above is a manual check. Record a table: case, OS and version, client build, result, message text if any.
*   After any code change: the same unit tests plus a repeat of the failed case on the platform where it failed.
*   Untested platforms are listed explicitly in the ADR amendment.

## Open questions for the author

1.  **Who tests Windows and Linux?**
    *   **The author tests on borrowed or dual-boot machines before release.** Mechanism: author installs Forever on a Windows machine and a Linux setup. Trade-off: full control and quick. Fails when the author has no spare machine or the Linux launcher setups are too varied to cover alone.
    *   **Players test after a release, through an issue template.** Mechanism: the Addon card plus a template that asks for OS, path and the error text. Trade-off: real layouts. Fails when the first release's install failure is the player's first impression (ADR 0034 journey 1 starts with the addon).
    *   **Ship macOS-only detection and paste field for the others, mark the rest unverified.** Mechanism: no extra testing. Trade-off: no delay. Fails when a path guess puts the wrong folder in "Use this folder?" on Windows; the confirm step limits the harm but the install may still be refused.
2.  **If the client does not ignore dot-prefixed folders, or the swap breaks a running game, what replaces staging in the AddOns folder?**
    *   **Stage in a directory next to `AddOns` (inside `Interface`) or in the app's data directory, then rename.** Mechanism: no leftover folder in the scanned location. Trade-off: the game never sees it. Fails across drives: a rename between filesystems fails, so the data directory option needs a copy and loses the atomic swap.
    *   **Name the stage with a character the client cannot treat as an addon name.** Mechanism: keep staging in `AddOns` with a different prefix. Trade-off: small code change. Fails if the client lists every directory regardless of its name.
    *   **Write in place with no stage.** Mechanism: overwrite files directly. Trade-off: no extra folders. Fails by leaving a half-written addon on a crash or lock, which ADR 0028 chose to avoid (decision "Install algorithm").
3.  **If a standard Windows user cannot write to Program Files, what does the app do?**
    *   **Show the plain error and the path, and tell the user to run the app as administrator.** Mechanism: no code beyond the message. Trade-off: simplest. Fails for players who do not know how, and running the whole app elevated widens its reach.
    *   **Offer a copy-the-files instruction with the folder opened.** Mechanism: the UI shows steps and a path to copy to. Trade-off: no privilege change. Fails the one-click goal of ADR 0028.
    *   **Drop Windows auto-install and document the manual path only.** Mechanism: remove Windows candidates. Trade-off: no wrong guesses. Fails the same goal on the platform with the most players, probably.
